# RAG 파이프라인 설계문서

## 전체 흐름

기업/질문 → P1 검색 계획 → 유형별 DART 후보 캐시/API → P2 선별 → ZIP·본문 준비 → 추가 문서 전문 청킹/small 색인 → LangGraph retrieve → generate → 인용 검사·추천 질문·화면.

LangGraph는 retrieve/generate 두 노드다. 데이터 수집과 색인 준비는 그래프 앞에서 실행한다. 동일 질문의 UI 세션 결과는 재사용하고, 문서 캐시는 P1/P2 채팅 캐시와 구분한다.

## 두 RAG 범주와 모델별 컬렉션

RAG 1은 기업 메타데이터, RAG 2는 외부 공시다. 모델의 벡터 공간이 달라 RAG 2를 물리 컬렉션 두 개로 나눴다. 두 모델의 벡터를 같은 컬렉션에 넣지 않는다.

| 컬렉션 | 내용 | 모델·차원 | 연간 기준 건수 |
| --- | --- | --- | --- |
| company_meta_bb94416ac449 | 고정 기업 텍스트 | large / 3,072 | 100 |
| disclosure_docs_bb94416ac449_c36c1707fb13 | 기존 선택 섹션 | large / 3,072 | 21,374 |
| disclosure_docs_4fbf39ae60bf_9f92ec141d8e | 나머지 전문 + 추가 선택 보고서 | small / 1,536 | 98,634 + 추가 분기 |

기존 .env의 GMS_EMBEDDING_MODEL은 large를 유지한다. 확장 모델·차원은 config/retrieval.json의 full_text_expansion에 지정한다. 실제 혼합 파이프라인 검증은 gpt-6.1-sol로 수행했다. 이후 사용자가 .env의 채팅 모델을 gpt-5.4-nano로 변경했으며 현재 그 설정을 유지한다. 변경 후 채팅을 다시 호출하지 않았다.

메타데이터에는 기업 ID/이름/종목/업종/기준기간/대표 접수번호/출처/해시를 저장한다. 문서에는 기업·문서·접수번호·보고서명·기준기간·접수일·출처 종류/URL·섹션/제목·청크 프로필·본문 해시·원문 시작/끝 위치를 저장한다. ID는 기업:접수번호를 포함한 섹션ID:프로필:순번:본문해시다.

## 전문 청킹과 중복 제외

1. 기존 ZIP과 파싱 자료를 재사용해 본문의 모든 섹션을 full_sections.jsonl로 구성한다. 표지·이사회·주석 등을 제목으로 제외하지 않는다.
2. 섹션 안에서 1,000자/200자 중복으로 재귀 분할한다. 긴 표의 반복 구분문에서 위치 추적이 건너뛴 비공백 구간은 실제 원문 위치를 그대로 잘라 보충한다.
3. 모든 청크의 시작/끝 위치와 본문·섹션 해시를 검증하고 섹션별 구간 합집합에 누락이 없는지 확인한다. 경계 공백만 허용한다.
4. 기존 large의 content_sha256과 같은 본문은 제외한다. 전문 120,008개 = 기존 21,374개 + small 확장 98,634개다. 합집합이 전문 범위와 일치하는지 별도로 검사한다.
5. 모델·제공자·차원별 임베딩 캐시를 사용한다. 변경분 upsert 후 해당 기업/접수번호 안에서만 과거 ID를 정리한다. OS 잠금으로 색인 상태의 동시 갱신을 막는다.

본문이나 원문 출처를 임의로 요약·추정하지 않는다. 표 병합 셀은 펼치고 이어지는 표에는 원래 앞부분·단위 문장을 덧붙인다.

## 추가 보고서의 자동 연결

P1은 사업·반기·분기 유형과 핵심어를 JSON으로 반환한다. DART 목록은 각각 A001/A002/A003으로 조회하며 동일 유형/기간의 최신 정정본을 후보로 삼는다. P2는 모든 후보의 selected/reason을 반환하고 자체 대표 사업보고서는 코드가 강제 포함한다.

선택한 보고서는 기업·접수번호·기간을 검증한 뒤 ZIP/파싱 캐시를 재사용한다. XML의 문서 코드와 회사 ID, 분기/반기의 표지 기준기간도 확인한다. 추가 문서는 report_chunks/프로필/기업/접수번호 경로에 전문을 청킹해 small 컬렉션에 색인한다. 대표 연간 보고서 재색인이 추가 문서를 지우지 않도록 삭제 범위도 접수번호로 제한한다.

완료 상태에는 접수번호·청크 수·청크 파일 해시를 기록한다. 파일·파싱 결과가 바뀌면 재사용을 막는다. 새 문서 임베딩은 allow_document_embedding으로 제어하며 large 대표 문서는 신규 임베딩을 금지하고 기존 것만 재사용한다.

## 모델별 검색과 병합

선택 기업 메타데이터는 large 컬렉션에서 항상 1건 포함한다. 질문은 large/small 각각의 모델로 임베딩하고 각 모델의 컬렉션만 검색한다. corp_code와 이번에 선택한 receipt_no 목록을 함께 필터링한다.

각 모델에서 벡터와 한국어 핵심어 순위를 RRF로 결합한 뒤, 모델별 결과도 1/(60+순위)로 병합한다. 서로 다른 모델의 코사인 거리를 직접 비교하지 않는다. 기업·접수번호·섹션·원문 위치·본문 해시로 중복을 제거한다. 최종 외부 근거는 최대 Top-k개, 기업 메타데이터는 별도 1개다. hybrid/RRF를 MMR이라고 부르지 않는다.

## 설정과 비교

| 값 | 현재 설정 | 이유 |
| --- | --- | --- |
| chunk_size / overlap | 1,000 / 200자 | 표·문단 문맥과 입력 크기 균형 |
| top_k / candidate_k | 5 / 20 | 답변 길이와 모델별 후보 수의 균형 |
| search_mode | hybrid | 의미 검색 + 실제 용어 일치 |
| base / expansion dimensions | 3,072 / 1,536 | 각 모델의 실제 기본 차원 |
| request_gap_seconds | 0.5초 | 동시 요청이 호출 시작 간격을 공유 |
| 추가 문서 배치/동시 요청 | 64 / 2 | 추가 문서 처리 지연 완화. 대량 CLI는 명시 옵션 사용 |

기존 large 모드에서 Top-k 3/5/8과 단일 섹션의 청크 1,000/200 대 600/100(2개 대 4개)을 실측했다. evidence/probe.json은 확장 전 관찰이다. 혼합 전문 코퍼스를 두 청크 설정으로 다시 임베딩하는 실험은 하지 않았다.

## 프롬프트와 표시

| 단계 | 역할·입력 | 출력·검증 |
| --- | --- | --- |
| P1 | 기업·질문에서 공시 검색 계획 추출 | keywords 1~5, report_types 허용 목록 JSON |
| P2 | 질문·계획·후보에서 문서 선별 | 후보 전체 판단 JSON, 누락/중복/가짜 ID 금지, 자체 문서 포함 |
| P3 | 번호 붙인 실제 근거만으로 초보자 해설 | 쉬운 설명·용어·한계, 문장에 [n] 인용, 기간/단위 구분 |

문서 안의 지시문으로 규칙을 바꾸지 않는다. 기간이 다른 보고서를 섞어 현재 조건으로 단정하지 않는다. 금융지주와 자회사, 평균급여와 신입 초봉을 구분한다. 근거가 없으면 확인 불가라고 답하며, 번호 검사는 의미 정확성 전체를 보장하지 않는다.

화면에는 실제 답변 인용 근거만 표시하고 추천 질문 전용 근거는 구분한다. 여러 보고서의 조회 기간과 각 원문의 보고서 유형을 표시한다. 무인용 안내, 키/색인 누락, 처리 상태, 금융 안내를 유지했다.

## 취업 준비 특화 기능과 한계

브리핑은 사업·전략·위험요인을 검색하고 원문 발췌 ID로 출처를 복원·검증한다. 사실·취업 준비 해석·면접 연습을 구분한다. 저장본 4개 기업은 재사용한다. 새 브리핑 생성은 CLI다.

검색은 2026-10-22까지의 수집 스냅샷을 사용하며 현재 상품 조건이나 채용 정보를 보장하지 않는다. 대화는 세션 단위다. 독립 프론트엔드, MMR, 서로 다른 종류의 출처 결합은 미선택이다.
